finance invoice, alliances, out-of-office, spam, newsletter, Hinglish RFP), each with a known

## Failure Cases I Did Not Fix

1. **Hinglish deal-value override (mirrors the brief's Example 12 exactly).** Emails with
   subject "Product enquiry" but a body stating a large deal value in Hinglish shorthand
   ("budget approx 1.2 cr allocated hai") were routed to `u_rohit`/`smb_enquiry` by the
   rule-based fallback, because its keyword scorer matches the *subject* string "product
   enquiry" before it ever looks at the parsed deal value. The correct answer (per Example 12)
   is `u_aarti`/`enterprise_rfp`, since ₹1.2cr is well above the ₹10L threshold regardless of
   how generic the subject line is. **Why I didn't fix it in the fallback:** the fallback is
   explicitly the degraded-mode path (see DECISIONS.md #1) — the real fix is that the primary
   Gemini classifier's prompt already encodes this exact trap as a worked example, so this
   failure mode should not occur when `GEMINI_API_KEY` is set. I did not have a live key to
   verify that claim end-to-end before this handoff; **verify this specific case against the
   live Gemini path before submitting** by ingesting an email shaped like Example 12 and
   checking the resulting task's `assignee_id`.

2. **`query_engine.py`'s intent router will misfire on genuinely novel question phrasing.**
   E.g. "which single company has sent us the most emails" doesn't match any pattern and falls
   through to the zero-match handler, which would incorrectly tell the user the answer is zero
   rather than saying it doesn't know how to compute that. This is a real gap, not just an
   edge case — see DECISIONS.md #5 for the reasoning and the fix I'd ship with more time
   (function-calling instead of keyword routing).

3. **No handling for attachments-only signal.** Several real-world RFPs in the brief's own
   worked examples arrive with the actual proposal document as an attachment and a thin email
   body ("Please find attached our RFP..."). Neither the rule-based fallback nor the current
   Gemini prompt reads attachment *content* (only the `attachments` filename list) — a company
   name or deal value that only appears inside an attached PDF will be missed and correctly
   come back `null`, which is the safe behavior per spec, but it does mean recall on
   `company_name`/`deal_value_inr` extraction is a hard ceiling below 100% until attachment
   parsing is added.
